## 1. 架构定位：方向是对的

模块的设计原则是**"确定性矢量 diff（占 80% 精度）+ 可选 LLM 语义层（占 20% 表达）"**——
不用多模态模型直接看两张图做 diff，而是先把图纸解析成结构化实体表，用几何算法精确比对，
再让 LLM 把结构化清单翻译成人话。这个分层是对的：**LLM 只负责表达，不负责判断**，
避开了模型幻觉直接影响比对结果的风险。

三条路径：

| source | 触发条件 | 说明 |
|---|---|---|
| `rule` | `provider: rule`（默认）或无 api_key | 规则摘要，离线可用 |
| `llm` | `provider: openai` + 有 api_key 且调用成功 | 模型生成 |
| `llm_fallback` | 调用成功前失败 | 回退规则摘要，并在日志告警 |

## 2. 评测方法

没有真实 API key 也能端到端验证——搭一个本地 mock 的 OpenAI 兼容接口，
让 `llm.py` 真的发 HTTP 请求过来，再把收到的请求 dump 出来检查：

```python
# 关键点：base_url 指向本地 mock
cfg['llm'].update(provider='openai', api_key='sk-test',
                  base_url='http://127.0.0.1:8123/v1')
```

mock 支持四种模式：`ok` / `500` / `bad`（返回结构非法 JSON）/ `slow`（挂起 60s）。

---

## 3. 实测：请求构造正确

`MODE=ok` 下捕获到的请求：

```
path          : /v1/chat/completions          ✅ URL 拼接正确
authorization : Bearer sk-test-key            ✅ 鉴权头正确
content_type  : application/json              ✅
payload_keys  : max_tokens, messages, model, temperature
system        : 163 字符（CAD 制图审核工程师角色设定）
user          : 3128 字符（变更清单 JSON）
```

**系统提示词质量不错**，明确要求"先一句话总览，再按删除/新增/修改/移动分类给要点，
并提示需要人工重点核对的地方"，还加了**"不要编造清单里没有的内容"**这句关键约束——
这是对幻觉的有效抑制。

## 4. 发现并修复的问题

### 4.1 【严重】清单无上限，大图纸必然打爆上下文

原实现直接 `json.dumps(changes)` 全量送入，实测膨胀情况：

| 变更数 | payload 字符 | 估算 token | 后果 |
|---|---|---|---|
| 10 | 3,942 | ~1.3k | 正常 |
| 200 | 78,802 | ~26k | 偏大 |
| 500 | 197,275 | ~66k | 接近上限 |
| **1000** | **396,037** | **~132k** | **超 gpt-4o-mini 128k 上下文** |
| **3000** | **1,194,408** | **~398k** | **必然失败** |

整层楼的暖通图改版产生上千处变更很常见，原实现在这类场景下会直接失败或烧掉大量费用。

**修复**：新增 `slim_changes()`，三招瘦身——

1. **剔除 `shape` 字段**：那是给渲染层画圈注用的（实测内容只是 `{"kind":"rect"}`），
   对 LLM 毫无意义却占 **27%** 的 payload；
2. **坐标降精度**：原值是 `3182.550068639724` 这种 16 位浮点，纯属无效精度，
   降到 1 位小数 `3182.6`；
3. **条数上限**：超出 `max_items`（默认 200）的部分改为统计概览，
   附 `_by_kind` / `_by_type` 让模型仍知道全貌。

效果：

| 变更数 | 修复前 | 修复后 | 压缩 |
|---|---|---|---|
| 10 | 3,912 | 2,042 | 48% |
| 1000 | 393,037 | 40,931 | **90%** |
| 3000 | 1,185,408 | 40,934 | **97%** |

### 4.2 【严重】0 处变更仍然调用接口

实测：空变更清单下照样发出 HTTP 请求。既白花钱，更糟的是——
mock 返回了"本次共检出 10 处变更"这种**与事实严重矛盾的内容**。
真实模型在空清单下同样可能凭空生成变更描述，属于典型的幻觉风险。

**修复**：`llm_summary()` 开头短路，无变更直接返回规则摘要。

### 4.3 【体验】超时 40 秒太长

实测失败时用户要**干等 41 秒**才拿到回退结果。批量任务下每个都等 40 秒不可接受。
摘要只是锦上添花，不该阻塞主流程。

**修复**：默认超时降到 **20 秒**（实测 21 秒完成回退），并开放 `timeout` 配置项。

### 4.4 【质量】规则摘要措辞问题

| 问题 | 原输出 | 修复后 |
|---|---|---|
| 为 0 的类型也列出来 | "共检出变更 2 处：新增 2 处、删除 0 处、修改 0 处、移动 0 处。" | "共检出变更 2 处：新增 2 处。" |
| 单图层说"主要集中" | "删除主要集中在图层：0(10)。" | "删除的 10 处全部位于图层：0。" |
| 单条移动说"多为" | "有 1 处发生位置移动，多为图元重排或整体平移。" | "有 1 处发生位置移动。"（≥3 处才加推测） |
| 无变更时留空标题 | 仍输出"【关键明细】" | 直接返回，不输出空标题 |

## 5. 规则摘要的真实能力边界

这点值得单独说。规则摘要统计准确、离线可用，但**没有语义理解能力**。

最能说明问题的例子（`samples/real`）：

```
[ADDED] LINE  x∈[2852,2852] y∈[1050,2050]   线条 长度≈1000.0 (Δx=0.0, Δy=-1000.0)
[ADDED] LINE  x∈[1852,3852] y∈[1550,1550]   线条 长度≈2000.0 (Δx=2000.0, Δy=0.0)
```

一条长 1000 的**竖线**、一条长 2000 的**横线**，且正交——稍有制图常识的人一看就知道
**"新增了十字中心线"**。但规则摘要只会原样罗列这两条线的坐标和长度，说不出这个判断。

这正是 LLM 层不可替代的价值：**模式识别与工程语义归纳**。规则能保证"不漏报"，
但"说人话、看出门道"得靠模型。所以配置 LLM 不是锦上添花，而是这个模块能否真正
服务于审图场景的关键。

## 6. 配置建议

```yaml
llm:
  provider: openai            # rule（离线默认） / openai
  base_url: "https://api.openai.com/v1"
  model: "gpt-4o-mini"
  api_key: ""                 # 留空自动走规则摘要
  temperature: 0.2            # 低温度，减少发挥
  max_tokens: 1200
  timeout: 20                 # 超时自动回退，别让摘要阻塞主流程
  max_items: 200              # 逐条送入上限，超出只给统计
  char_budget: 60000          # 字符硬上限，超出截断
```

**选型建议**：

- **离线/内网环境**：保持 `provider: rule`，摘要可用，只是没有语义归纳；
- **有 API key**：切 `openai`，摘要质量显著提升，值得那点成本；
- **大图纸（上千处变更）**：务必保留瘦身配置，否则请求会失败；
- **国产模型 / 自建服务**：改 `base_url` 即可，代码走的是 OpenAI 兼容协议。

## 7. 遗留事项

1. **未做真实模型调用验证**。本报告基于 mock 服务端到端验证请求/响应链路，
   实际摘要的**文字质量**需用真实 API key 另行评估（不同模型差异较大）。
2. **无重试机制**。当前失败即回退，对偶发网络抖动可考虑加一次重试。
3. **`rule_summary(changes, cfg=None)` 的 `cfg` 参数未被使用**，保留仅为接口兼容。
